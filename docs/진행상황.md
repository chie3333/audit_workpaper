## 작업 로그

새 회차는 맨 위에 추가한다.

### 2026-10-27 · 분류 검토 절차 추가
- **된 것**
  - 새 절차 `cash.classification_review` (템플릿 `classification_review`): 항목별 금액·만기 구분·취득일·만기일·사용제한·회사 분류·감사인 판단 분류·판단 근거·근거 위치
  - 엔진: 취득→만기, 대상일→만기 일수와 분류별 합계(회사 vs 감사인 판단)·재분류 금액만 계산. 분류는 제안하지 않음. 분류가 다른 행은 발견 사항 기록 요구
  - 남은 작업 점검: 사용제한 미확인, 제한 내용·판단 근거 미기록, 날짜 누락·순서 오류 등
  - 화면·엑셀(5. 분류 검토표: 기간표·분류표·분류별 합계, 일수·합계는 수식)
  - 가상 사례: 가상 차이(주) A-210 — K02 정기예금 취득→만기 181일, 회사 현금성 vs 감사인 판단 단기금융상품, 발견 사항 후속 확인 중. 예금증서_K02.xlsx 추가
  - 템플릿별 필수 자료(`required_documents`)·기본 기록 구조를 일반화. 기존 대사 콘텐츠 해시는 그대로
  - 테스트 13개 추가 (전체 49개 통과, LibreOffice 필요한 3개 건너뜀)
- **안 된 것**: 엑셀 수식 결과 = 엔진 계산 대조는 LibreOffice가 없어 실행하지 못함(수식 문자열만 확인), 분류 검토 안내 문구 실무 검토(전부 'AI 초안')
- **알려진 문제·미확인**
  - 서식에서 분류 검토 절차 위치 미확인, 기업회계기준서 1007·1001호 문단 미확인 → 안내는 '보완 설명·미확인'
  - 주장 CL 적용은 대화에서 정한 대로 '사용자 검토 완료'로 표시함
- **다음 할 일**: LibreOffice 설치 후 수식 대조 테스트 실행, 분류 검토 안내 문구 검토, 기준서 문단 확인 후 근거매핑 추가

### 2026-10-27 · 가상 회사 자료 엑셀
- **된 것**
  - 가상 사례 3종이 근거 위치로 가리키는 회사 자료를 엑셀로 생성: `samples/sources/{정상,차이,자료부족}/` 10개 파일 (`scripts/make_sample_sources.py`)
  - 셀 위치·금액이 `app/samples.py`의 근거 위치와 같은지, 입수/요청 상태대로 파일이 있는지, 가상 표시가 있는지 테스트 7개 추가
  - 명세서 표시 합계는 회사가 적은 값으로 보고 수식이 아닌 값으로 넣음 (차이 사례는 일부러 틀린 합계)
- **안 된 것**: 계좌를 늘린 연습용 자료, 보조원장 거래 내역(기말잔액만 있음)
- **알려진 문제·미확인**: K02 정기예금을 현금및현금성자산 잔액에 포함한 것은 기존 가상 사례 설정을 그대로 따른 것 (분류 판단은 하지 않음)
- **다음 할 일**: 치치가 가상 자료를 열어 조서 입력 연습, 필요하면 계좌를 늘린 연습용 자료

### 2026-10-27 · 1단계 구현
- **된 것**
  - 1단계 v1 구현: 조서 생성 → 안내 확인 → 입력·계산 → 저장(리비전) → 다시 열어 수정 → 엑셀 다운로드
  - 콘텐츠: 출처 목록(근거매핑과 같은 위치만 허용), 경영진 주장, 공통 템플릿 `schedule_recon`, 현금 설정 `cash.schedule_recon` (v0.1.0)
  - 엔진: 계산 5종, 점검 13종, 상태 3종 분리. 빈칸은 0으로 계산하지 않음
  - 엑셀: 한 시트(30행 초과 시 상세 시트), 차이·합계 수식, 가상 데이터·미검토·미해결·원본/수정본 표시
  - 가상 사례 3종과 자동 테스트 32개 (웹 계산 = 엑셀 수식 결과 대조 포함), 화면 클릭 테스트, 모바일 폭 확인
- **안 된 것**: 치치의 직접 사용 확인, 안내 문구 실무 검토(전부 'AI 초안'), 증빙 업로드, 다른 계정·절차
- **알려진 문제·미확인**
  - 수정본 재대사 시 보조부 금액은 이전 대사에서 복사됨 (보조부도 바뀌었다면 직접 고쳐야 함)
  - 발견 사항의 금액은 기록 시점 값이라, 이후 대사 금액이 바뀌면 화면에 "연결된 차이가 현재 0 또는 미입력"으로만 표시됨
  - 엑셀 행 높이는 글자 수로 어림잡아 정함. 아주 긴 문장은 잘려 보일 수 있음
  - XBRL 연계 문의 받음 (미결정)
- **다음 할 일**: 치치가 가상 사례로 직접 써보기, 안내 문구 검토, XBRL 연계를 어느 단계에 둘지 결정

## 문서 목록과 관리 원칙

| 문서 | 위치 | 내용 | 언제 고치나 |
|---|---|---|---|
| 기획서 | 저장소 `docs/기획서.md` | 목표, 범위, 단계 구분, 설계 원칙 | 방향이 바뀔 때만 (결정기록을 모아서 반영) |
| 근거매핑 | 저장소 `docs/근거매핑_현금명세서대사.md` | 기준서·서식 문단 ↔ 콘텐츠·설계 요소 | 절차나 계정을 추가할 때 |
| 결정기록 | 저장소 `docs/결정기록.md` | 날짜, 결정, 이유, 대안 | 결정할 때마다 |
| 진행상황 | 저장소 `docs/진행상황.md` (이 문서) | 작업 목록, 작업 로그 | 작업이 끝날 때마다 |
| README | 저장소 `README.md` | 실행 방법과 현재 상태 | 기능이 바뀔 때 |
| 콘텐츠 검토 상태 | 저장소 `content/*.json` | 안내 문구별 출처 태그·검토 상태 | 문구를 쓰거나 검토할 때 |
| 테스트 | 저장소 `tests/` | 가상 사례 3종 | 기능을 바꿀 때 |

- 같은 내용을 두 군데 쓰지 않는다. 코드로 확정된 내용은 코드를 기준으로 보고, 기획서에는 개요만 둔다.
- 기획서는 자주 고치지 않는다. 바뀐 내용은 결정기록에 먼저 쓰고 모아서 반영한다.
- 안내 문구의 검토 상태는 문서가 아니라 콘텐츠 JSON 안에 남긴다.
